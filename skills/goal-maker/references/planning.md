# 계획 작성과 수렴

## 정본과 추적

- brief는 사용자 의도·R/AC, plans는 D 결정과 범위, spec은 S 계약, impl_plans는 T 실행 절차를 소유한다. 하류에서 상류 의미를 조용히 바꾸지 않는다.
- 형제 문서는 파일+절+식별자로 인용한다. 행 번호는 안정적인 계약 참조가 아니다.
- 공유 계약 소유자와 소비자, 계약 개정/수락 상태를 기록한다. 제공자가 바꾼 계약을 소비자가 수락하기 전에는 관련 문서를 수렴으로 처리하지 않는다.
- 문서당 2,000행 이하로 분할한다. 필수 절·완료 표식·누락/부분 작성·예상보다 작은 문서·깨진 참조를 내용과 함께 확인한다. 분량이 길다는 이유로 실행 가능하다고 판정하지 않는다.

## 리뷰 관점

bounded의 plans/spec은 정합성·최소성·완결성, impl_plans는 구현가능성을 추가한다. architectural은 이 전 관점에 영역 간 교차정합을 추가한다. 가능하면 독립 fresh 컨텍스트에 정본·검토 범위·관점만 전달한다. 리뷰 worker는 읽기 전용이며 같은 파일을 동시에 수정하지 않는다.

문서 결함은 사실 오류·모순·실행 불가·목표 완료에 필요한 누락이다. 없어도 합의 목표가 성립하는 것은 확장 제안이다. 지적은 ID·심각도·근거·위치/식별자·영향·수정안을 갖추고 실제 정본에 대조해 오탐/중복을 제거한다.

## 수렴 루프

1. 검토 → 지적 타당성 확인 → 결함 수정 → 확장 제안 처리/격리 → 영향 재검토를 반복한다.
2. 보안 CRITICAL/HIGH가 실제 요구 이행을 위협하면 필요한 범위 개정과 이유를 기록해 반영한다. 외부 작업의 새 권한까지 자동 승인된 것은 아니다.
3. 큰 변경은 다음 라운드, 작은 변경은 축약 재확인한다. 2라운드부터 diff와 영향 중심으로 검토한다. 공유 계약 변경은 영향을 받는 전체 문서를 확인한다.
4. 수렴 조건은 결함 CRITICAL/HIGH=0, 미처리 제안=0, 미수락 계약 요청=0이다. MEDIUM/LOW의 잔여 사유와 영향도 남긴다.
5. 같은 차단 유형이 과반이면 표면 수정 대신 계약/인용/소유 경계를 고친다. 고정 3회 상한을 두지 않는다. 사용자가 정한 비용/시간 상한에 도달하면 미수렴 상태·잔여·재개 조건을 보고한다.

WORK_ROOT/review/plans.md, spec.md, impl_plans.md에 라운드·검토자/컨텍스트·대상 revision·지적·처리·최종 판정을 남긴다. 자동 구조 검사는 이 리뷰를 대체하지 않는다.

## 인계 준비도

pre-work는 실제로 사람이 해야 하는 권한 부여/자료 제공 등만 포함한다. READY에는 실제 근거, DEFERRED에는 안전하게 연기할 조건, NOT_APPLICABLE에는 이유, BLOCKED에는 재개 조건이 필요하다. 필수 환경 증거가 없으면 초안은 가능하지만 frozen 실행 패키지로 만들지 않는다.

변경 시 이전 frozen 패키지를 `revisions/<revision>/` 등에 보존하고 영향 계획·명세·task와 검증을 다시 수렴시킨다. 활성 work run의 goal.json을 덮어쓰지 말고 허브와 영향 task 정지를 먼저 조정한다. 후속 phase의 구현을 지금의 검증 조건으로 요구하지 않는다.
