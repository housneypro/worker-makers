# 계획 작성과 수렴

## 정본과 추적

- brief는 사용자 의도·R/AC, plans는 D 결정과 범위, spec은 S 계약, impl_plans는 T 실행 절차를 소유한다. 하류에서 상류 의미를 조용히 바꾸지 않는다.
- 형제 문서는 파일+절+식별자로 인용한다. 행 번호는 안정적인 계약 참조가 아니다.
- 공유 계약 소유자와 소비자, 계약 개정/수락 상태를 기록한다. 제공자가 바꾼 계약을 소비자가 수락하기 전에는 관련 문서를 수렴으로 처리하지 않는다.
- 문서당 2,000행 이하로 분할한다. 필수 절·완료 표식·누락/부분 작성·예상보다 작은 문서·깨진 참조를 내용과 함께 확인한다. 분량이 길다는 이유로 실행 가능하다고 판정하지 않는다.

## 재사용 판정 의무

기술 결정을 내리기 전에 실제 함수·컴포넌트·데이터 구조·현재 스택·사용 선례를 조사한다. plans의 각 D-ID는 다음 결정표를 갖는다. 작은 변경은 한 행으로 충분하며 로컬 변수나 설명 문장마다 결정을 새로 만들지 않는다.

| 결정 | 연결 R/AC | 조사한 기존 후보·위치 | 판정 | 선택과 필요성 | 신규 비교 ID |
|---|---|---|---|---|---|
| D-ID | 합의 기준 | 파일·심볼·설정과 조사 사실 | 기존 / 신규 | 최소 변경으로 기준을 충족하는 이유 | 신규일 때만 |

`기존`은 확인한 자산을 재사용하거나 필요한 부분만 수정하는 경우다. 새 함수·테이블·의존성·컴포넌트·공통 추상화 등을 도입하는 결정은 `신규`로 기록한다. 후보가 없으면 실제 조사 범위와 부재 근거를 쓴다. 빈 저장소에 가상의 재사용 후보를 만들지 않는다. 기존 후보/판정이 없거나 신규 비교 ID가 빠졌으면 plans 리뷰에 넘기지 않는다.

## 신규 도입 허용 조건

신규 결정마다 기존 자산의 최소 수정과 제안 경로를 나란히 비교한다. 변경 파일·영향 모듈·기존 호출부/계약의 회귀 범위는 실제 조사로 확인한 수치와 위치를 사용한다. 새 의존성·설정·migration·운영/복구 부담도 포함한다. 모르는 값을 0이나 임의 점수로 채우지 않는다.

| 비교 ID·대안 | 기존 후보/변경 위치 | 변경 파일·영향 모듈 | 호출부·계약 회귀 근거 | 추가 의존성·운영 부담 | 채택/기각 이유 |
|---|---|---|---|---|---|
| A-ID / 기존 최소 수정 | 조사 근거 | 확인한 수치 | 해당 위치·영향 또는 없음의 근거 | 실제 추가 부담 | 기준 충족 여부 |
| A-ID / 신규 도입 | 구체 제안 | 확인한 수치·계획 범위 | 보존/변경할 계약 | 도입·유지·복구 부담 | 필요한 예외와 근거 |

다음 중 하나가 객관적으로 확인되고, 제안한 추가 구조가 그 문제를 푸는 최소 범위일 때만 신규를 채택한다.

- 기존 방식으로 합의된 R/AC를 충족할 수 없다. 사용자가 새 인터페이스/기능을 명시한 경우도 해당 요구와 부재 근거를 연결한다.
- 기존 방식이 확정된 비변경 경계를 침범하거나 확인된 호출부/계약 회귀를 만들며, 제안 경로는 이를 피한다.
- 기존 최소 수정의 변경/영향 범위가 실측상 더 크고, 신규 경로가 추가 의존성과 유지·운영 부담을 고려해도 더 작은 해법임을 설명할 수 있다.

파일 수나 코드 줄 수가 작다는 사실만으로 예외를 인정하지 않는다. 필요성이 성립하지 않으면 기존 방식의 최소 변경을 선택한다. 근거가 부족한 신규 결정은 조사하거나 미확정으로 남기며 실행 가능한 frozen 계획으로 넘기지 않는다. 필요성이 입증된 범위의 기술 선택에는 별도 승인 의식을 추가하지 않는다. 실제 요구/권한 변경만 기존 합의 절차로 확인한다.

## 합리화 차단

아래 이유만으로 구현 범위를 넓히지 않는다.

- 더 깔끔하다 / 미래에 확장할 수 있다 → 현재 실패하는 AC·계약이나 측정된 유지 비용이 없으면 backlog.
- 이왕 수정하는 김에 인접 코드도 정리하자 → 현재 완료에 필요한 변경인지 별도로 판정한다.
- 리뷰어가 HIGH라고 했으니 반영하자 → 심각도와 필수성은 별개다. 실제 결함/목표 실패 근거를 대조한다.
- 계획을 상세하게 쓰려면 구조·task·문서가 더 필요하다 → 실행 설명을 구체화하고 구현 구조/범위는 유지한다.
- 보안/검증은 많을수록 좋다 → 적용 위험·완료 조건과 대응하지 않으면 자동 확대하지 않는다.

## phase·검증 확대 제한

bounded는 단일 phase를 기본으로 한다. 독립 task가 여럿이라는 이유나 문서 분량만으로 phase를 늘리지 않는다. 추가 phase는 앞 단계의 실제 산출물·계약·검증 통과가 후행 착수에 필요한 이유와 gate를 기록한다. 병렬 task 묶음은 실행 배치이며 의미 없는 phase 분할을 정당화하지 않는다.

각 검증 ID는 관찰할 AC·공유 계약·허용 범위의 필수 위험과 연결한다. 기존 검증이 어떤 실패를 놓치는지 확인한 뒤 필요한 최소 사례/명령을 추가한다. 같은 기준을 충분히 입증하는 검증을 중복하지 않는다. 현재 변경의 코드/보안 리뷰는 수행하되 무관한 기능·환경으로 검토 범위를 넓히지 않는다. 부하·장애 주입·다중 환경 하네스 등은 현재 완료 조건에 필요할 때만 계획한다.

없어도 합의 목표가 성립하는 구조 개선·미래 대비·추가 검증은 backlog다. 범위 확대는 사용자의 실제 요구 변경 또는 목표 이행을 위협하는 검증된 보안 CRITICAL/HIGH에 한해 이유와 영향 R/AC를 기록한다. 외부 실행 권한은 별도로 유지한다.

## 리뷰 관점

bounded의 plans/spec은 정합성·최소성·완결성, impl_plans는 구현가능성을 추가한다. architectural은 이 전 관점에 영역 간 교차정합을 추가한다. 가능하면 독립 fresh 컨텍스트에 정본·검토 범위·관점만 전달한다. 리뷰 worker는 읽기 전용이며 같은 파일을 동시에 수정하지 않는다.

최소성 리뷰는 재사용 판정의 실제 후보, 신규 예외의 비교 근거, 합리화로 숨긴 확대, phase/gate 의존, 검증 ID의 완료 기준 대응을 각각 확인한다. 신규안보다 단순한 기존 수정으로 해결되는 반례를 코드에서 찾고 비교 수치와 회귀 주장을 재확인한다. 위 제약 중 미충족 항목이 있으면 해당 계획을 수정/격리하고 수렴으로 선언하지 않는다.

문서 결함은 사실 오류·모순·실행 불가·목표 완료에 필요한 누락이다. 없어도 합의 목표가 성립하는 것은 확장 제안이다. 지적은 ID·심각도·근거·위치/식별자·영향·수정안을 갖추고 실제 정본에 대조해 오탐/중복을 제거한다.

## 수렴 루프

1. 검토 → 지적 타당성 확인 → 결함 수정 → 확장 제안 처리/격리 → 영향 재검토를 반복한다.
2. 보안 CRITICAL/HIGH가 실제 요구 이행을 위협하면 필요한 범위 개정과 이유를 기록해 반영한다. 외부 작업의 새 권한까지 자동 승인된 것은 아니다.
3. 큰 변경은 다음 라운드, 작은 변경은 축약 재확인한다. 2라운드부터 diff와 영향 중심으로 검토한다. 공유 계약 변경은 영향을 받는 전체 문서를 확인한다.
4. 수렴 조건은 결함 CRITICAL/HIGH=0, 미처리 제안=0, 미수락 계약 요청=0이다. MEDIUM/LOW의 잔여 사유와 영향도 남긴다.
5. 같은 차단 유형이 과반이면 표면 수정 대신 계약/인용/소유 경계를 고친다. 고정 3회 상한을 두지 않는다. 사용자가 정한 비용/시간 상한에 도달하면 미수렴 상태·잔여·재개 조건을 보고한다.

WORK_ROOT/review/plans.md, spec.md, impl_plans.md에 라운드·검토자/컨텍스트·대상 revision·지적·처리·최종 판정을 남긴다. 자동 구조 검사는 이 리뷰를 대체하지 않는다.

## 인계 준비도

pre-work는 실제로 사람이 해야 하는 권한 부여/자료 제공 등만 포함한다. READY에는 실제 근거, DEFERRED에는 안전하게 연기할 조건, NOT_APPLICABLE에는 이유, BLOCKED에는 재개 조건이 필요하다. 필수 환경 증거가 없으면 초안은 가능하지만 frozen 실행 패키지로 만들지 않는다.

변경 시 이전 frozen 패키지를 `revisions/<revision>/` 등에 보존하고 영향 계획·명세·task와 검증을 다시 수렴시킨다. 활성 work run의 goal.json을 덮어쓰지 말고 허브와 영향 task 정지를 먼저 조정한다. 후속 phase의 구현을 지금의 검증 조건으로 요구하지 않는다.
