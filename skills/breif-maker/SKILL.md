# breif-maker

사용자가 확정한 이름은 `breif-maker`, 산출물 이름은 `brief.md`다. 요구의 의미와 합의를 소유한다. 기술 설계·정확한 타입/스키마·구현 순서·개발은 goal-maker/work의 책임이다. 요구 정제와 질의응답은 이 패키지에 포함된 규약으로 수행한다.

## 진입

일반 요구에는 아래 정제 절차를 적용한다. goal-maker가 질문 ID와 체크포인트를 전달하면 [질의응답 모드](references/clarification.md)를 적용하고 응답을 반환한다. goal-maker를 재귀 호출하지 않는다.

최초 진입에서 사용자가 지정한 제품 프로젝트 root와 작업명을 확정한다. 도구 clone이나 임시 worktree의 `.git`을 제품 root로 선택하지 않는다. 새 작업만 다음 명령으로 공간을 만든다. 기존 작업은 같은 경로를 재사용한다.

```text
python <SKILL_ROOT>/scripts/wm.py init --project <PROJECT_ROOT> --name <작업명>
```

산출물은 반환된 WORK_ROOT에 둔다. 설치 스킬 디렉터리에 사용자 작업 문서를 쓰지 않는다. 스크립트는 Python 3.11+ 표준 라이브러리만 사용한다. 경로는 실제 셸에 맞게 인용한다.

## 요구 정제

1. 대화·제공 자료·적용 AGENTS.md·관련 코드/문서를 읽는다. 기존 명시적 합의, 관찰 사실, 가정, 미결정을 구분한다. 충분한 기존 요구는 그대로 활용하고 형식적인 질문을 반복하지 않는다.
2. 결과를 바꾸는 미결정을 분류한다. 사용자 목적·선호·범위·권한은 사용자 선택, 현재 동작은 조사, 구현 방법은 goal-maker의 기술 선택이다. 현재 코드가 미래 요구의 정답이라는 가정을 하지 않는다.
3. 다음 결정을 실제로 바꾸는 질문부터 묻는다. 목적/핵심 사용자·주요 시나리오·성공/실패 동작·경계/비목표·수용 기준·운영 제약 중 빠진 부분만 다룬다. 가능하면 구체 사례와 상호 배타적인 선택지, 추천 이유/영향을 제시한다. 도구가 지원하면 비동기 질문 중 독립 조사는 계속한다. 미응답·시간 경과는 답이 아니다.
4. 제품 방향이 갈리면 의미 있게 다른 접근을 비교한다. 이미 명확한 작은 변경에는 인위적인 대안 개수나 긴 인터뷰를 강요하지 않는다. 구현 아키텍처를 이 단계에서 확정하지 않는다.
5. [brief 템플릿](assets/brief.md)을 실제 내용으로 채운다. R-ID → 관찰 가능한 AC-ID를 연결하고 비목표·예외·합의 출처·조사 사실·기술 미확정·인계 제약을 구분한다. 가정이 승인처럼 보이지 않게 표시한다.
6. 미결정이 요구/범위/수용 기준을 막는지 확인한다. 기존 사용자 승인과 명시적 선택은 승계한다. 새로운 중요한 요구 선택만 확인한다. 충분하면 `status: agreed`와 revision, 실제 합의 출처를 남기고 마지막 완료 표식을 넣는다. 단순히 문서를 썼다는 이유로 합의를 만들지 않는다.

새 사실로 방향이 바뀌면 영향 R/AC만 개정하고 이전 합의와 frozen 문서는 보존한다. 변경 요약과 영향 하류를 goal-maker에 전달한다. 요구 정제는 구현·의존성 설치·DB 적용·원격 발행 권한을 자동 부여하지 않는다.

타당성 조사만 요청받으면 근거·한계·권고로 종료한다. 구현 goal을 만들어야 한다고 가정하지 않는다. 필요한 실험은 기존 권한 범위 안에서만 수행하고 제품 개발로 자동 승격하지 않는다.

## 인계

WORK_ROOT, brief revision, 합의 상태/출처, R/AC, 비목표, 기술 미확정, 관련 자료를 반환한다. 해결되지 않은 사용자 선택이 있으면 `needs_user`/`blocked`와 정확한 재개 조건을 보고한다. 다음 단계는 같은 세션의 goal-maker이며 사용자가 이미 계획 작성을 요청했다면 수동 재호출을 요구하지 않는다.
